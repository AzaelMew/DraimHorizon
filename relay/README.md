# Relay для собственного хоста

Отдельный Python-сервис для Claim Borders. Minecraft-сервер ничего не устанавливает и не пересылает: мод подключается к вашему `wss://relay.example.com/v1/relay` напрямую. Relay проверяет подписи идентичности Ed25519 и направляет непрозрачные зашифрованные сообщения между подключёнными клиентами одного realm. Содержимое сообщений он не расшифровывает и не журналирует. Формат обмена описан в [PROTOCOL.md](PROTOCOL.md).

Сертификаты самоподписанные: имя и Minecraft UUID — заявления владельца ключа, а не проверка владения аккаунтом. При добавлении друга сверяйте его код ключа через доверенный канал. Realm разделяет каталоги и маршруты; это не пароль. При необходимости ограничьте доступ общим токеном оператора.

## Запуск через Docker Compose и HTTPS

Нужны собственный сервер с Docker Compose, домен с DNS A/AAAA на этот сервер и доступные TCP 80/443 (UDP 443 необязателен). Скопируйте **весь каталог `relay/`** на свой сервер и выполните в нём:

```sh
cp .env.example .env
chmod 600 .env
python3 -c 'import secrets; print(secrets.token_urlsafe(32))'
```

В `.env` задайте `DOMAIN=relay.example.com`. При желании вставьте созданный токен в `RELAY_ACCESS_TOKEN=` и укажите тот же токен в настройке relay клиента. Токен передаётся заголовком `Authorization: Bearer …`, никогда в URL. Пустое значение разрешает доступ всем, кто предъявил корректную подпись ключа. Не отправляйте `.env` в Git и не публикуйте токен в чате.

```sh
docker compose up -d --build
curl --fail https://relay.example.com/healthz
```

Ожидаемый ответ: `["ok","1.0.0"]`. Caddy получает и обновляет TLS-сертификат автоматически. Клиентам задайте `wss://relay.example.com/v1/relay`. Relay доступен только во внутренней Docker-сети, наружу выставлен Caddy. DNS и сертификаты настраиваются на вашем сервере; публикация из этого репозитория не выполняется.

```sh
docker compose ps
docker compose down
```

Стандартные логи контейнеров отключены; не включайте access/debug-логи прокси с заголовками авторизации или телами сообщений. Healthcheck не требует токена и раскрывает только статус и версию.

## Запуск без Docker

Требуется Python 3.12 или новее:

```sh
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
python -m dhrelay --host 127.0.0.1 --port 8765
curl --fail http://127.0.0.1:8765/healthz
```

`RELAY_ACCESS_TOKEN`, `RELAY_HOST`, `RELAY_PORT` и `RELAY_TRUSTED_PROXY_CIDRS` читаются из окружения. Файл `.env` автоматически читает только Compose: для ручного запуска задайте переменные в вашем менеджере сервиса. Без параметров сервис слушает `127.0.0.1:8765`. Используйте systemd или другой менеджер для автозапуска и отдельного непривилегированного пользователя.

Для существующего Caddy, установленного на том же хосте, блок сайта:

```caddy
relay.example.com {
    reverse_proxy 127.0.0.1:8765 {
        header_up X-Real-IP {remote_host}
    }
}
```

Прокси должен поддерживать WebSocket upgrade и сохранять `Authorization`. Снаружи используйте WSS; HTTP/WS допустим только на локальном соединении между прокси и сервисом. Сервис не доверяет `X-Forwarded-For`. Заголовок `X-Real-IP` используется только от TCP-адресов из `RELAY_TRUSTED_PROXY_CIDRS` (через запятую; по умолчанию только loopback). Caddy всегда перезаписывает этот заголовок адресом TCP-клиента. Compose задаёт отдельную сеть `172.29.50.0/24`, адрес Caddy `172.29.50.2` и доверие только его `/32` плюс loopback; лимит 8/IP поэтому относится к реальным клиентам. Если сеть пересекается с вашей инфраструктурой, согласованно измените подсеть, оба адреса и доверенный `/32` в `compose.yaml`. Для другого прокси добавьте только его точный адрес/CIDR и обязательно настройте перезапись `X-Real-IP`; пустое значение отключает доверие заголовку.

## Ограничения и хранение

Одновременно допускаются 256 соединений, 64 аутентифицированных участника realm, 8 соединений с одного IP; незавершённые аутентификации тоже учитываются в глобальном/IP лимитах. Срок challenge — 10 секунд. Входящее сообщение — не более 16 КиБ, непрозрачный пакет — не более 8192 байт; очередь клиента — 128 сообщений, входной буфер WebSocket — 4 кадра, скорость — 10 сообщений/с с начальным запасом 20. Переполненный получатель отключается, медленный клиент не задерживает остальных. Повторное подключение одного ключа отклоняется до закрытия прежней сессии. Неизвестный или отключённый адресат и другой realm не получают сообщений; отправителю возвращается `recipient_offline`. Подтверждений доставки и офлайн-очереди нет.

Базы данных, истории сообщений, отложенной доставки, сохранения replay-кэша и файлов пользователей нет. Перезапуск очищает присутствие и очереди, клиенты подключаются заново. Fresh challenge привязывает аутентификацию к конкретному соединению. Проверку replay зашифрованных сообщений и доверия друзьям выполняют клиенты; relay не разбирает их содержимое. Оператор видит ключи, realm, имена из сертификатов, IP, время, объём и адресатов трафика; E2E скрывает содержимое, но не эту метаинформацию.

Для резервного копирования достаточно собственной `.env` (безопасное хранилище) и конфигурации. Docker-тома `caddy_data`/`caddy_config` содержат состояние Caddy и сертификаты: их можно резервировать, чтобы избежать повторной выдачи сертификатов. Данных переписки для копирования нет. Обновление: сохраните локальную `.env`, замените исходники и выполните `docker compose up -d --build`.

## Проверка

```sh
python -m unittest discover -s tests -v
```

Тесты поднимают реальные WebSocket-соединения только на `127.0.0.1`, создают ключи Ed25519 в памяти, проверяют доставку непрозрачного сообщения, изоляцию realm, подделку подписи, replay challenge, дубликат ключа, очистку присутствия, ограничения, таймаут, токен и HTTP healthcheck.
